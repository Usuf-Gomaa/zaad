# Content updates after launch — Umrah and future Hajj

This workflow is prepared for a future authorized launch. No launch or religious publication is authorized by this document.

1. **Capture provenance.** Keep incoming files immutable, record their date/hash and author-supplied status. Current sources are the v2 review draft plus v2.1 source-check addendum. Run `npm run sources:identity` after changing either file and commit/review the generated identity. `npm run review:import` reimports the base narrative, not approval; rerun source identity and all checks afterwards. Store additional future source documents in the fingerprint list deliberately. Never silently edit a generated file or label unchanged feedback as reviewing new text.
2. **Keep stable IDs.** Maintain the 51 current Umrah IDs and namespace mappings. Existing checklist progress and personal duas must retain their keys. Add new content IDs without reusing old ones. Hajj has a prepared namespace but remains disabled for public publication until separately reviewed and tested. Do not turn it on just to preview a draft; use the private review overlay. Data schema stays IndexedDB v2; a future essential migration requires dedicated compatibility tests, a backup/recovery plan and owner review.
3. **Research claims individually.** Record the exact bounded claim, audience, source URL/title, hadith/verse/fatwa locator, short directly observed text where permitted, context, evidence-to-claim rationale, identity/date/method and exceptions. Distinguish candidate existence, automated partial source observation, complete claim coverage and genuine qualified approval. Do not fill liturgical formulas from memory, invent grades/English verification or copy approval from an adjacent claim. Claims about repetition/timing/gender/validity/fidyah need their own coverage. Compare disputed positions with their own sources; do not convert an attributed preference to consensus.
4. **Prepare private review.** Update structured content outside UI components, preserve Arabic originals, add both UI language labels. Any English explanation of research status is separate from an approved religious translation. Build local offline `.review-dist/` or authenticated network-only `.staging-dist/` as appropriate. Never publish either as `dist/`. Follow [the staging runbook](REVIEWER_STAGING_DEPLOYMENT.md); a viewing warning or localhost runner is not authentication.
5. **Collect actual review.** An invited scholar reads full drafts, evidence, scope and unresolved notes, enters feedback and exports JSON/CSV. Feedback is local and does not grant approval. The owner receives exports through an agreed secure channel. Resolve all 14 correction flags and the itemized research/questions with a documented response. Record actual reviewer identity, relevant qualifications, actual approval date, covered wording/locale/claims and any conditions only when genuinely provided; do not use Codex as the qualified reviewer.
6. **Review translations separately.** Obtain independent review of English meaning, provenance and suitability; preserve the original Qur'an/hadith Arabic and check chosen orthography directly. Record exact source and actual translation reviewer. Approval of Arabic does not automatically approve English. The locale publication gate must continue withholding incomplete English religious records.
7. **Promote deliberately.** Only after real review, extract individually approved content into public release modules with complete evidence/scope/disputes/applicability/translation metadata. Update the strict explicit `published.ts` allowlist and the currently-zero-public-content test intentionally through owner-reviewed code changes. Do not import the full private registry into public code. The publication checker currently requires zero approved records; its expected set must only be changed to the explicitly approved IDs with recorded review. Automated checks can enforce completeness, not verify a scholar's credentials or religious correctness.
8. **Verify before release.** Run the full commands in [public readiness](PUBLIC_RELEASE_READINESS.md), regenerate status/matrix, inspect both artifacts for leaks and verify backup v1/v2 compatibility, language changes while writing, offline cold reload, trip/checklist isolation, feedback history and safe update activation. Reconfirm no analytics, accounts, advertising, backend or personal-content requests. Update Arabic/English release notes, app version and religious content edition independently; never increment the database merely to release content.
9. **Obtain owner deployment authorization.** Present exact tested artifact/build ID, content IDs/locale approvals, unresolved gaps, domain/hosting cost and rollback target. Keep draft review and public release decisions separate. Do not deploy from an approval of source checking alone.
10. **Deploy and monitor after authorization.** Follow immutable artifact/atomic switch instructions, retain previous public hashed assets, keep the same public origin and preserve browser data. The waiting service worker activates only after explicit confirmation and drained writes. Updates require an online reachable server and the application to run/open; there is no promise that a closed/offline device receives them. Recheck installation, language bundles, headers, backups and storage after updating. If a content issue arises, block the affected record, issue a new gated build and follow the rollback/communication plan; already cached or downloaded text cannot be remotely recalled from offline devices.

Review notes, source checks and qualified approvals are distinct audit events. Exported reviewer data can contain names, unpublished drafts and personal comments; retain and share it according to the owner's agreed privacy policy. Hosting error/connection logs require their own minimal retention policy even without app analytics.
